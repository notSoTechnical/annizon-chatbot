# Annizon Chatbot 🤖 try on annizon.com

A RAG (Retrieval-Augmented Generation) customer-service chatbot for Shopify stores.
Ask it about return/shipping policies — it answers from your real store policies, never making things up.

## How RAG works (3 steps)

Think of it like cooking:

1. **Ingest （备菜）** — Fetch your policy pages, clean out navigation junk, cut text into small chunks (~500 chars each), save to `chunks.json`.
2. **Retrieve （挑菜）** — When a customer asks a question, find the 3 most relevant chunks.
3. **Generate （炒菜）** — Send the chunks + the question to the AI. It answers ONLY from the chunks.

```
Customer question
      ↓
find_relevant() → top-3 chunks      (retrieval.py)
      ↓
"Policy excerpts: <chunks>          (chatbot.py / app.py)
 Question: <question>"
      ↓
Gemini answers from excerpts only
```

The system-prompt rule that prevents hallucinations:

> "Answer ONLY using the policy excerpts below. If the answer is not in the excerpts, say you don't know."

## Files

| File | What it does |
|------|--------------|
| `ingest.py` | Fetches policy pages (shipping / refund / privacy / terms) from the store, extracts clean text with BeautifulSoup (`div.shopify-policy__body`), chunks it into ~500-char pieces, saves `chunks.json`. Run once, or whenever policies change. |
| `retrieval.py` | `find_relevant(question, top_k=3)` — embeds the question with Gemini `text-embedding-004` and returns the top 3 chunks by dot-product similarity (understands meaning, not just matching words — e.g. "shipped" matches "shipping" policy). Chunk embeddings are cached once per process. Three-layer fallback: Gemini → local `sentence-transformers` model (optional) → keyword overlap. |
| `chatbot.py` | Command-line chatbot: retrieve → build prompt → ask Gemini → print answer. Loops until you type `quit`. |
| `app.py` | Streamlit web UI version of the same RAG pipeline. This is what gets deployed to the cloud. Chat history lives in `st.session_state` (Streamlit re-runs the script on every interaction). Also hosts the **📧 Email a human** fallback form (see below). |
| `widget.js` | One-line embed for any Shopify theme: floating chat bubble (bottom-right) → click opens the chatbot in a panel (embedded via iframe). Served through jsDelivr CDN. |
| `triage.py` | AI ticket triage: `categorize(issue, client)` asks Gemini to classify a message (`shipping` / `refund` / `return` / `product` / `other`) and `TEAMS` routes it to the right inbox. `USE_TEAM_INBOXES = False` for now → everything lands in `info@annizon.com` with a `[category]` subject tag. |
| `chunks.json` | The policy chunks (generated by `ingest.py`, not hand-written). |
| `requirements.txt` | Python dependencies. |
| `.github/workflows/nightly.yml` | Nightly CI: re-ingests policies (`python ingest.py`) then runs `pytest tests/ -v`. Scheduled `0 6 * * *` (2 AM ET), plus manual dispatch. |

## Email a human fallback 📧

When the bot says "I don't know", it nudges the customer to the **📧 Still need help? Email a human** form (in `app.py`): they enter their email + question, and it's emailed to `info@annizon.com` automatically via [Resend](https://resend.com).

Flow:

```
Bot: "I don't know" → hint appears under the answer
      ↓
Customer fills email + question → clicks "Send to support"
      ↓
send_to_support() → AI triage → POST https://api.resend.com/emails
      ↓
info@annizon.com receives it, customer's address set as reply-to
```

Setup (one-time):

1. **Verify your domain in Resend** — Resend → Domains → add `annizon.com`, then add the DNS records it shows (DKIM `TXT resend._domainkey` + two SPF `CNAME`s for `rsend` / `send`) to your domain's DNS, and click Verify.
2. **Create an API key** — Resend → API Keys → create a key with **Sending** access (it shows only once — copy it immediately).
3. **Add it to Streamlit Secrets** — Streamlit Cloud → your app → Manage app → Settings → Secrets → add a new line `RESEND_API_KEY="re_..."` under the existing `GEMINI_API_KEY` line → Save (the app reboots).

Notes:

- `send_to_support()` validates the email format and fails gracefully (friendly message, no crash) if the key is missing or the send fails.
- The `from` address is `Annizon Support <support@annizon.com>` — this is why the domain must be verified in step 1.
- Keys never go in the repo — same rule as `GEMINI_API_KEY`.

### AI triage: auto-routing to teams 📨

Before sending, `categorize()` (in `triage.py`) asks Gemini to classify the message into one category — `shipping`, `refund`, `return`, `product`, or `other` — and routes it to the matching team inbox:

```python
TEAMS = {
    "shipping": "shipping@annizon.com",
    "refund": "refund@annizon.com",
    "return": "return@annizon.com",
    "product": "product@annizon.com",
    "other": "info@annizon.com",
}
```

Two safety nets (because AI is probabilistic):

- If the model replies with something unexpected → falls back to `other`.
- If the API call itself fails → falls back to `other` (the form never crashes).

`USE_TEAM_INBOXES = False` for now: the team addresses don't exist as real mailboxes yet, so everything is delivered to `info@annizon.com` with a `[category]` tag in the subject (e.g. `[refund] Customer question from ...`) — filter by tag in your inbox. Once you create the aliases at your mail host, flip the flag to `True` and mail routes for real.

The test suite covers this without needing an API key: `test_categorize_routes_with_stub_client` swaps in a fake LLM client (dependency injection) and checks both routing and the fallbacks.

## Nightly pipeline 🌙

Every night at 2 AM ET, GitHub Actions re-runs `ingest.py` to re-fetch the store's policy pages and rebuild `chunks.json`, then runs the full pytest suite — including the anti-hallucination tests. The bot's knowledge refreshes daily with zero manual work: if a policy changes, the next morning's chunks already reflect it, and the tests will catch it if something broke.

```yaml
# .github/workflows/nightly.yml
- cron: "0 6 * * *"      # 2 AM ET every night
- run: python ingest.py  # re-fetch policies -> fresh chunks
- run: pytest tests/ -v  # verify retrieval + guardrails
```

The `GEMINI_API_KEY` for CI lives in the repo's Actions Secrets — never in the code.

## Backup embedding — offline, optional 🔋

If the Gemini embedding API is unreachable, `find_relevant()` falls back in two stages:

1. **Local model** (`sentence-transformers` / `all-MiniLM-L6-v2`, ~90MB) — no API key, no network needed after the first download. It embeds with its own model, so its vectors are never mixed with Gemini's.
2. **Keyword overlap** — last resort, always available.

Setup (one-time, optional):

```bash
pip install sentence-transformers   # pulls torch; model downloads on first use
```

It's deliberately **not** in `requirements.txt` (torch is heavy for the Streamlit free tier). If the package isn't installed, the code skips straight to keyword fallback — nothing breaks, nothing to configure.

## RAG Notes

**Chunk**: a policy page is too long for the bot to read at once, so `ingest.py` cuts it into ~500-character slips and saves them to `chunks.json`. This store: 4 policy pages → 77 chunks.

**Each chunk is a dict**:
```python
{"source": "refund", "text": "Returns accepted within 30 days..."}
```
- `source` = a stamp saying which policy page this chunk was cut from (`refund` / `shipping` / ...)
- `text` = the chunk's content
- `c` = short for "chunk"; in `[c["text"] for c in chunks]` it takes turns being each chunk

**Vector**: turn a sentence into a list of numbers that represents its meaning. Similar meanings → similar numbers.
- Real numbers come from Google's API: `genai.embed_content(model="models/text-embedding-004", content="...")` → 768 numbers
- 768 is Google's choice: this model describes one meaning with 768 numbers
- Dot product measures "how similar": bigger dot product = closer meaning = the chunk the bot picks to answer

**Embedding models across providers**:

| Provider | Model | Dimensions | Best for |
|---|---|---|---|
| Google | `text-embedding-004` (this bot) | 768 | text |
| Google | `gemini-embedding-001` | 3072 | text |
| Google | `gemini-embedding-2` | 3072 (128–3072) | text, image, video, audio, PDF |
| Google (Vertex) | `multimodalembedding@001` | 1408 | text, image, video |
| OpenAI | `text-embedding-3-small` | 1536 | text |
| OpenAI | `text-embedding-3-large` | 3072 | text |
| OpenAI | `CLIP ViT-B/32` | 512 | text, image |
| DeepSeek | `deepseek-embedding-v2` | 1536 | text |
| xAI | `grok-embedding-v1` | configurable | text |
| Cohere | `embed-english-v3.0` | 1024 | text |
| Cohere | `embed-v4.0` | 1536 (256–1536) | text, image |
| Mistral | `mistral-embed` | 1024 | text |
| Mistral | `codestral-embed` | 1024 | code |
| Voyage | `voyage-code-3` | 2048 (256–2048) | code |
| Voyage | `voyage-multimodal-3.5` | 1024 | text, image, video |
| Local | `all-MiniLM-L6-v2` | 384 | text |

(Anthropic/Claude has no embedding API — people pair Claude with Voyage, Cohere, or OpenAI embeddings.)


**Bigger ≠ always better.** More dimensions = more room for fine distinctions, but training quality matters more: OpenAI's `text-embedding-3-large` truncated to 256 dims can beat the older 1536-dim `ada-002`. Judge by benchmark scores (MTEB), not dimension count.

**Tradeoff**: bigger dimensions can store more fine-grained meaning, but cost more — larger vectors to store, slower dot-product scoring, slower retrieval. That is why 768 is a popular sweet spot, and why some models let you truncate (e.g. the `dimensions` param) when speed matters more than the last bit of accuracy.

## Run your own model (data never leaves your machine)

Why: every question sent to a third-party API is data shared with that vendor. Banks and hospitals already self-host for this reason. The practical path is **self-host + fine-tune**.

**Step 1 — local embeddings (already wired in):**
```bash
pip install sentence-transformers
```
`retrieval.py` automatically falls back to the local `all-MiniLM-L6-v2` model when the Gemini API is unreachable — on that path no question text ever leaves your machine.

**Step 2 — local chat model (replaces the Gemini API):**
1. Install Ollama from [ollama.com](https://ollama.com).
2. `ollama pull llama3.1` (or `qwen2.5`), then `ollama run llama3.1` to chat in your terminal.
3. Point `chatbot.py` at `http://localhost:11434` (Ollama's OpenAI-compatible endpoint) instead of the Gemini API.

Note: an Intel Mac has no GPU — it works but is slow; Apple Silicon is much faster. Good enough to learn the plumbing.

**Step 3 — fine-tune on your own data (later):**
1. Collect Q&A pairs: real customer questions + your ideal answers.
2. Fine-tune an open embedding model with `sentence-transformers` (or a chat model with `unsloth`) on a free Colab GPU.
3. Swap the fine-tuned model into Step 1 / 2.

You do not need Step 3 until your domain has jargon the base models misunderstand — 77 policy chunks + stock models is plenty to start.

### In CI (GitHub Actions)

The small embedding model runs fine on CI runners; the big chat model does not.

```yaml
# .github/workflows/nightly.yml — verifies the local fallback with no API key
- name: Test local embedding fallback (no API key)
  run: |
    pip install sentence-transformers
    env -u GEMINI_API_KEY pytest tests/test_chatbot.py -v -k "retrieval"
```

Notes:
- `sentence-transformers` (~90MB model) installs in 1–3 minutes on a GitHub runner — fine for a nightly job. It stays OUT of `requirements.txt` because torch is too heavy for Streamlit's free tier (the deployed app).
- A full chat model (Ollama / llama3.1, several GB) is too heavy for CI runners — that layer is covered by mocked tests instead.
- Editing workflow files via API needs the `Workflows` permission on your GitHub token.

### From scratch (what it really takes)

The full recipe:

1. **Data**: billions of text pairs (embeddings) or trillions of tokens (chat model). Collecting and cleaning data is most of the work.
2. **Architecture**: BERT-style encoder for embeddings, GPT-style decoder for chat. Start from a known architecture — nobody invents a new one on the first try.
3. **Hardware**: GPUs, with distributed training (PyTorch + DeepSpeed / FSDP) across many of them.
4. **Evaluate**: MTEB leaderboard for embeddings; standard benchmarks for chat.

**Start small**: train a *tiny* model from scratch on free Colab to learn the full loop — e.g. `nanoGPT` (a small GPT trainable in hours) or a tiny BERT on a small dataset. Same steps, toy scale.

## Auto-crawl (no manual policy URLs)

Give the bot any website URL — it crawls the site itself, finds policy/FAQ-like pages first, and builds `chunks.json` in the same format `ingest.py` produces:

```bash
python crawler.py https://example.com --max-pages 40 --out chunks.json
```

- Respects `robots.txt`, stays on the same domain, 0.5s delay between requests.
- Pages with shipping / refund / FAQ / policy hints in the URL are crawled first.
- Output is drop-in compatible with `retrieval.py` — no other code changes needed.

## Multi-store

One deployment serves many stores. Each store's chunks live in their own file:

```
chunks/annizon-com.json
chunks/hm-com.json
```

- `find_relevant(question, top_k=3, store_id="hm-com")` answers from that store's chunks only — no cross-store leakage.
- A store id is derived from the website domain (`store_id_for_url()` in `crawler.py`): `https://www.hm.com` → `hm-com`.
- Unknown store ids fall back to the legacy `chunks.json`, so old deployments keep working.
- The sidebar has a store picker to switch which store the chat answers as.

## Merchant onboarding (password-gated)

In the app sidebar: **🏪 Onboard a new store** — enter a website URL, the crawler builds that store's chunk file, and the chatbot is ready. No code, no command line.

The write path is locked: set `ADMIN_PASSWORD` in Streamlit Secrets (app Settings → Secrets). Without it, onboarding shows as disabled; with it, only the password holder can add stores.

## Security notes

- **No keys in code.** `GEMINI_API_KEY`, `RESEND_API_KEY`, and `ADMIN_PASSWORD` live in Streamlit Secrets / env vars. The repo is safe to keep public.
- **Cloning the repo does not affect the deployed app.** A clone is just a copy of the code — it runs under someone else's account with their own keys. Your deployment is tied to your Streamlit account and your Secrets.
- The only write path on the live app is merchant onboarding, gated by `ADMIN_PASSWORD`.
